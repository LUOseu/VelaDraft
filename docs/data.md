# Data and supervision

How a training run turns your image-text rows into drafter supervision. The
short version: **your rows are prompts; the answers that train the drafter are
regenerated by the target model** (target-native regen), so supervision follows
the same distribution the deployed drafter will face.

## Accepted JSONL shapes

One JSON object per line (JSONL - not a pretty-printed JSON array). Three
shapes are accepted (see `vlm_dflash/data/schema.py`):

```jsonl
{"id":"row-001","image":"cat.jpg","question":"What is in this image?","answer":"A cat sleeps on a sofa."}
{"id":"row-002","messages":[{"role":"user","content":"<image>Explain the chart."},{"role":"assistant","content":"..."}],"image":"chart.png"}
{"id":"row-003","conversations":[{"from":"human","value":"<image>What is shown?"},{"from":"gpt","value":"..."}],"image":"doc.png"}
```

`image` is resolved against `--images-dir` (`dataset.jsonl_images_dir` /
`dataset.images_dir`) when it is not an absolute path.

Multi-image / multi-turn rows use schema v2: a flat `images` list plus
`image_turns` (the conversation index each image belongs to, same order as
`images`):

```json
{"id":"row-004","images":["a.jpg","b.jpg"],"image_turns":[0,2],
 "conversations":[{"from":"human","value":"<image>\nWhat is in the first image?"},
                  {"from":"gpt","value":"... (context, not supervised)"},
                  {"from":"human","value":"<image>\nAnd the second?"},
                  {"from":"gpt","value":"... (regenerated and supervised)"}],
 "schema":"vlm-dflash-data-v2"}
```

## What is supervised: regeneration and `last_turn_only`

During the `regen` stage the frozen target greedily regenerates the supervised
answer(s); the regenerated token ids become the training targets (capture
re-checks that the prompt re-renders bit-exactly). The dataset's own `answer`
text is **prompt material, not the label**.

- **Single-turn rows**: the answer is regenerated and supervised.
- **Multi-turn rows, default `regen.multi_turn_mode: last_turn_only`**: earlier
  assistant turns are kept verbatim as teacher-forced context; **only the last
  assistant turn is regenerated and supervised**. Eval renders the same
  original history, so training and eval follow one protocol.
- **`all_turns` (opt-in, experimental)**: every assistant turn is regenerated
  progressively (conditioned on already-generated earlier turns) and all of
  them are supervised. Eval still renders the dataset history, so all-turn
  artifacts are only comparable within their own protocol.

In the row-004 example above, the first `gpt` turn is context and the second is
the supervised (regenerated) answer. See `vlm_dflash/target/regen.py` for the
authoritative semantics and `R-20261014-19` in `docs/plan/RUN_LOG.md` for the
recorded post-remediation smoke.

## Row filtering: prepare and regen can both shrink your pool

`--limit` (CLI) / `dataset.slice` (config) is the number of **training** rows;
`dataset.val_size` validation rows are drawn **on top**, so the pool needs at
least `limit + val_size` usable rows. With a 32-row pool and `--limit 32` the
val split is empty (prepare warns; eval then has nothing to read).

| Stage | Filter | Default |
| --- | --- | --- |
| prepare (`llava_instruct` source only) | `dataset.min_answer_chars` | config-specific (e.g. 600 in the 2K recipes) |
| prepare (all sources) | pool must be larger than `limit + val_size` | - |
| regen (all rows) | `regen.min_response_tokens` drops rows whose *regenerated* answer is shorter | 16 in the examples, 128 in the long-answer recipes |

JSONL input itself is **not** length-filtered. After each stage, check the real
counts: `data/manifest.json` (`num_train` / `num_val`) and
`regen/regen_stats.json` (`num_kept`, skip reasons). Short-answer datasets
(e.g. COCO captions) need a recipe with a small `min_response_tokens` - the
default 128-token recipes will drop nearly all of them.

## Split, seed and reproducibility

- Rows are sampled without replacement using `dataset.seed`; train/val stay
  disjoint (`data/manifest.json` records both `src_index` lists and a
  `rows_sha256` digest that is stable across reruns).
- Images are copied/verified into `<run>/data/images` with per-file hashes;
  capture later re-checks image bytes, so a swapped file fails loudly.
- Same-seed reruns reproduce the data and regen selection; bf16 capture and
  training are protocol-reproducible, not bitwise deterministic (see
  `docs/measured-runs.md`).

## Running the stages

The `train` command runs prepare -> regen -> capture -> train for you; the
stage scripts (`scripts/prepare_data.py`, `scripts/capture_features.py`, ...)
remain the advanced interface. A small end-to-end example:

```bash
python examples/train_from_jsonl.py \
  --target "$VLM_DFLASH_TARGET" \
  --jsonl data/rows.jsonl --images-dir data/images \
  --limit 32 --steps 60
```

For full runs and long training sessions, continue with
[training.md](training.md).
